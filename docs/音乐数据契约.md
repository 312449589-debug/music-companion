# 任务03：音乐数据契约

唯一源文件：`backend/app/schemas/composition.py`。JSON Schema 和前端 TypeScript 类型由脚本生成，不能各改一套。

## 数据含义

- `schema_version`：当前结构版本 1.0，后续字段变化需同步版本和转换方式。
- `composition_id`、`title`、`origin`：标识同一作品；`diagnostic` 是固定检查样例，`ai` 才是模型创作结果。
- `tempo_bpm`、`key_signature`、`time_signature`：全曲唯一速度、调性和拍号，不在音符上定义另一套速度/调性。
- `ppq`：一个四分音符对应的整数 tick 数。样例采用480，仅是工程时间单位，不限制作品长度。
- `tuning`：弦号到实际发声音高的映射。1为高音弦 E4/MIDI64，6为低音弦 E2/MIDI40。JSON 的弦号键是字符串，Python 解析后为整数。
- `measures`：小节列表，记录编号、顺序、起始时间、长度和可选和弦名。
- `events`：旋律和伴奏分别标记，可以同时发声。`onset_tick` 是从全曲起点算的绝对位置，不是从当前小节算；`duration_ticks` 是持续时间。
- `kind`：音符或休止。音符必须有弦号、品位及 MIDI 音高；休止不填写这三项。0品表示空弦。
- `notation_duration`、`dotted`、`tie`：记谱时值、附点和延音标记。1/2/4/8/16表示全、二分、四分、八分、十六分音符；结构允许不等于生成会自动使用全部组合。
- `source_composition_id`、`constraints`：为后续保留原 BPM/调性的整段重新生成记录来源和约束；本任务只定义字段，不实现生成逻辑。

不存可信的手填时长，后续任务05从事件位置计算。弦位音高一致性、小节是否填满、时长上限、同弦冲突、跨度和听感属于后续规则检查，结构通过不意味着这些已通过。

## 亲自验证

双击根目录 `检查音乐数据.command`，应看到“结构检查通过”、`origin: diagnostic`、80 BPM、两小节、melody/accompaniment 两个声部，以及标准定弦。该操作不会改变网页或调用 AI。

也可以在项目根目录执行：

```bash
backend/.venv/bin/python backend/scripts/check_composition.py
backend/.venv/bin/python backend/scripts/check_composition.py --invalid-string
backend/.venv/bin/python backend/scripts/check_composition.py --missing-field
backend/.venv/bin/python backend/scripts/export_contracts.py --check
```

前一条通过；第二条故意将第一音符弦号改为7，应指出 `measures.0.events.0.string`；第三条缺少速度，应指出 `tempo_bpm`。两条错误诊断返回退出码1，不修改原始样例。第四条检查 Python/JSON Schema/TypeScript 是否同步。

如果修改数据字段，在项目根目录运行 `backend/.venv/bin/python backend/scripts/export_contracts.py` 重新生成契约和类型，再执行同步检查和前端构建。
